# **🏥 Aptino Policy-Aware Claim Engine**

An enterprise-grade, multi-agent AI system for evaluating health insurance claims against complex policy documents. Built for the Aptino Generative AI Engineering assessment.

This engine overcomes the limitations of standard RAG pipelines (hallucinations, context overflow, and generic reasoning) by utilizing a **LangGraph-orchestrated multi-agent workflow**, a **Hybrid Search \+ Reranking retrieval pipeline**, and **Strict Pydantic Contracts** for reliable, structured decision-making.

## **🏗️ 1\. Architecture & Design Decisions**

### **A. Architecture Diagram**

graph TD  
&nbsp;&nbsp;&nbsp;&nbsp;A\[Raw Claim JSON\] \--\> B\[Case Analysis Agent\]  
&nbsp;&nbsp;&nbsp;&nbsp;B \--\> |Investigation Plan| C\[Policy Evidence Agent\]  
&nbsp;&nbsp;&nbsp;&nbsp;C \<--\> |Hybrid Search \+ FlashRank| D\[(Policy Vector/BM25 Store)\]  
&nbsp;&nbsp;&nbsp;&nbsp;C \--\> |Retrieved Chunks| E\[Coverage & Exclusion Agent\]  
&nbsp;&nbsp;&nbsp;&nbsp;E \--\> |Coverage Findings| F\[Decision Agent\]  
&nbsp;&nbsp;&nbsp;&nbsp;F \--\> |Draft Decision & Citations| G\[Validation Agent\]  
&nbsp;&nbsp;&nbsp;&nbsp;G \--\> |Validation Status| H\[Final Pydantic Response\]

### **B. RAG & Retrieval Strategy (Hybrid \+ Reranking)**

Relying solely on dense vector search often misses strict policy terminology, acronyms, or numerical limits. This system utilizes a three-stage pipeline to ensure maximum precision:

1. **Semantic Chunking:** The policy PDF is parsed using Markdown converters to respect document hierarchy (Headers, Sections). Traceability metadata (Chunk ID, Section) is injected directly into each chunk.  
2. **Hybrid Search:**  
   * *Dense Retrieval (FAISS \+ Gemini Embeddings):* Captures semantic intent (e.g., matching "broken bone" to "fracture").  
   * *Sparse Retrieval (BM25 Okapi):* Captures exact keyword matches, crucial for policy codes and specific medical terminology.  
3. **Lightweight Reranking:** Fused results are reranked using FlashRank (an ONNX-based reranker) to prioritize the most relevant clauses within a tightly constrained context window, keeping latency low without heavy PyTorch dependencies.

### **C. Multi-Agent LangGraph Workflow**

Instead of relying on a single, overloaded LLM prompt to parse, retrieve, reason, and decide, the cognitive load is distributed across five specialized agents operating via a strict ClaimGraphState dictionary.

1. **Case Analysis Agent:** Extracts facts from the raw JSON claim and dynamically generates an investigation\_plan (a list of semantic queries tailored to the claim).  
2. **Policy Evidence Agent:** Executes the investigation plan against the Hybrid Retriever and loads specific, deduped policy chunks into the state.  
3. **Coverage & Exclusion Agent:** Evaluates the extracted facts *strictly* against the retrieved evidence to identify exclusions, waiting periods, and limits.  
4. **Decision Agent:** Synthesizes prior findings into a strict enum (ADMISSIBLE, NOT\_ADMISSIBLE, NEEDS\_REVIEW) and maps material claims to exact Chunk IDs for citations.  
5. **Validation Agent:** Acts as an anti-hallucination guardrail. It independently verifies that every citation generated by the Decision Agent is explicitly supported by the retrieved text.

### **D. Resilience & Strict Contracts**

* **Pydantic Validation:** All agent outputs are forced into strict Pydantic schemas using with\_structured\_output, leveraging Python's Literal types to guarantee valid decision enums.  
* **Safe LLM Invocation:** A BaseLLMAgent class wraps all calls. If an LLM encounters a transient error, rate limit, or schema failure, the system falls back to a safe NEEDS\_REVIEW state rather than crashing the LangGraph execution.

## **⚖️ 2\. Trade-offs**

* **Accuracy vs. Latency:** Implementing a sequential, 5-agent LangGraph pipeline ensures high reasoning accuracy and zero-hallucination citations, but increases end-to-end latency (\~35-55s) compared to a single-shot LLM prompt. We optimized for safety and precision over pure speed.  
* **Local Reranking vs. Compute:** FlashRank (ONNX) was selected for local reranking to keep the deployment lightweight, avoid third-party API costs, and prevent sensitive medical data transmission. This trades off the marginally higher semantic precision of a heavy PyTorch Cross-Encoder model.  
* **Synchronous API vs. Streaming:** The FastAPI endpoint holds the connection open while the graph executes. While simpler to deploy, it prevents true token-by-token streaming to the frontend.

## **⚠️ 3\. Known Limitations**

* **Complex PDF Tables:** The current markdown parser can struggle with highly nested or complex tables in the policy document. Sub-limits deeply buried in complex tabular formats may occasionally lose semantic structure during extraction.  
* **API Rate Limiting:** Heavy concurrent batch processing is currently limited by Google Gemini API free-tier limits. Enterprise deployment would require a provisioned throughput tier to scale effectively.  
* **Language Support:** The system is currently optimized exclusively for English-language policy documents and claims.

## **📊 4\. Evaluation Results**

The engine was evaluated automatically via tests/evaluate.py against 12 public datasets and 5 custom edge cases (testing cosmetic exclusions, accident FIRs, and strict 30-day waiting periods).

* **Validation Pass Rate:** 100% (The Validation Agent confirmed all citations were explicitly grounded in the policy text; no hallucinations detected).  
* **Abstentions (NEEDS\_REVIEW):** The system successfully abstained when evidence was lacking (e.g., missing FIRs for accidents, undefined experimental treatments, facility definitions), satisfying the requirement for \>2 abstentions.  
* **Average Latency:** \~35 \- 55 seconds per case (expected for sequential multi-agent chain-of-thought).

## **🚀 5\. Local Setup & Execution**

### **Prerequisites**

* Python 3.9+  
* A valid Google Gemini API Key

### **Installation**

1. Clone the repository:  
   git clone https://github.com/yourusername/aptino-claim-engine.git  
   cd aptino-claim-engine

2. Create and activate a virtual environment:  
   python3 \-m venv venv  
   source venv/bin/activate  \# On Windows: venv\\Scripts\\activate

3. Install dependencies:  
   pip install \-r requirements.txt

4. Set up Environment Variables:  
   Create a .env file in the root directory:  
   GOOGLE\_API\_KEY=your\_google\_api\_key\_here  
   BACKEND\_URL=http://127.0.0.1:8000

### **Running the System**

**1\. Start the FastAPI Backend:**

python3 \-m src.api.main

*The API will start at http://localhost:8000 and load the LangGraph state machine into memory.*

**2\. Start the Streamlit Frontend (In a new terminal):**

streamlit run frontend/app.py

*The interactive UI will open in your browser, complete with execution tracing and dynamic loaders.*

**3\. Run the Automated Evaluation Suite:**

python3 tests/evaluate.py
